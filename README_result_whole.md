## Process CPU Offload Results

### Methodology

These rows measure CPU work consumed by the decoder process itself, not
whole-system CPU load. qprof `apps-proc-cpu-metrics` reports aggregate apps
processor load, so it can include Android background services, adb/qprof
overhead, thermal services, and unrelated work. It is diagnostic-only here and
is not used to quantify CPU offload.

For each workload, `measure_process_cpu.sh` launches the benchmark and samples
per-thread CPU ticks from:

```text
/proc/<pid>/task/*/stat
```

The process workload uses `exec ./binary ...`, so the measured PID is the
decoder binary itself: `hqc*_decode_bench_arm64_android` for CPU scalar and
`hqc_host` for NPU/FastRPC. The script records elapsed time, total decodes, and
process CPU ticks, then computes:

```text
process_cpu_s = delta(utime + stime ticks across all threads) / CLK_TCK
process_cpu_pct = 100 * process_cpu_s / elapsed_s
cpu_ms_per_decode = 1000 * process_cpu_s / total_decodes
reduction_vs_cpu = 100 * (cpu_ms_per_decode_cpu_scalar - cpu_ms_per_decode_backend)
                         / cpu_ms_per_decode_cpu_scalar
```

`CPU ms/decode` is the main offload metric because it normalizes host CPU work
by completed decodes, making faster NPU runs comparable with slower CPU scalar
runs.

## FastRPC Boundary Overhead

### Methodology

These rows isolate where FastRPC overhead appears in the current NPU path. The
main NPU benchmark uses one `hqc_decode_bench` FastRPC call that runs the full
decode loop on the cDSP, so the remote-call boundary cost is amortized over all
decodes. To expose the fine-grained cost, the same binary now also supports:

- `open-close`: repeated FastRPC session open/close, measured separately from
  steady-state calls.
- `ping`: repeated no-op FastRPC calls with scalar input/output only.
- `payload-in`: one input buffer from host to cDSP, DSP checksum only.
- `payload-out`: one output buffer from cDSP to host.
- `payload-inout`: input buffer plus output buffer round trip, no HQC decode.
- `decode-one`: one FastRPC call per decode, using the same DSP-resident
  fixture corpus as the batched benchmark.
- `bench`: the existing batched path, one FastRPC call for `iters * 16`
  decodes.

Command:

```sh
ADB=/mnt/c/Temp/ADB/platform-tools/adb.exe \
LEVELS="128 192 256" REPEATS=1 PING_CALLS=1000 OPEN_CLOSE_CALLS=20 \
PAYLOAD_CALLS=1000 DECODE_ONE_CALLS=1000 BENCH_ITERS=100 \
scripts/measure_android_fastrpc_overhead.sh
```

  batched cDSP throughput with amortized FastRPC overhead. It should not be
  presented as the latency of a production API that makes one FastRPC call per
  decapsulation.

## RS Roots Memory-Clear Trim

### Methodology

This is a small memory-write reduction in Reed-Solomon root search. The old
code cleared the whole GF(2^8) support space:

```c
memset(error, 0, 1 << PARAM_M);
```

Since `PARAM_M = 8`, this always cleared `256` bytes. The downstream HQC
decoder only consumes the shortened RS support `[0, PARAM_N1)`, so the retained
code clears only the bytes that are actually read:

```c
memset(error, 0, PARAM_N1);
```

This means the clear size becomes `46` bytes for HQC-128, `56` bytes for
HQC-192, and `90` bytes for HQC-256. This is not a VTCM/L2/layout change; it
only removes unnecessary memory writes.

### Results

| HQC | Scope | Result | Delta |
| --- | --- | --- | ---: |
| HQC-128 | Full decode | PASS | -0.14% |
| HQC-128 | Stage 6 RS roots | PASS | -0.41% |
| HQC-192 | Stage 6 RS roots | PASS | -0.23% |
| HQC-256 | Stage 6 RS roots | PASS | -0.14% |

Interpretation:

- The gain is small because only a short `memset` is removed.
- The change is still retained because it matches the actual consumer range and
  the speedup is positive across tested parameter sets.

## FastRPC Shared-Buffer Memory/Cache Probe

### Methodology

This probe adds a `buffer-bench` FastRPC entry point that sends a ring of
codeword buffers from the host to cDSP, decodes them on cDSP, and writes the
messages back into a host-visible output buffer. It is meant to separate the
question "does the decode kernel benefit from explicit input staging or L2
prefetch?" from the previous fixture-only DSP benchmark.

Tested host allocation modes:

- `malloc`: 128-byte aligned normal host memory.
- `rpcmem-cached`: FastRPC rpcmem cached buffer with static-map hint.
- `rpcmem-uncached`: FastRPC rpcmem uncached buffer.

Tested DSP-side access modes:

- `direct`: decode directly from the shared input buffer.
- `copy`: copy each shared input codeword into a 128-byte aligned DSP local
  stack buffer before decode.
- `l2fetch`: issue `Q6_l2fetch_AR` for the next codeword, then decode directly
  from the shared input buffer.
- `vtcm`: not retained in the benchmark binary. Two VTCM experiments were run
  and rejected because they did not beat direct shared-buffer decode.

Command:

```sh

export ADSP_LIBRARY_PATH="$PWD;/vendor/dsp/cdsp;/vendor/lib/rfsa/adsp;/vendor/lib64/rfsa/adsp"
./hqc_host buffer-bench malloc direct 100 16
./hqc_host buffer-bench malloc copy 100 16
./hqc_host buffer-bench malloc l2fetch 100 16
./hqc_host buffer-bench rpcmem-cached direct 100 16
./hqc_host buffer-bench rpcmem-cached copy 100 16
./hqc_host buffer-bench rpcmem-cached l2fetch 100 16
./hqc_host buffer-bench rpcmem-uncached direct 100 16
./hqc_host buffer-bench rpcmem-uncached copy 100 16
```

  `HAP_compute_res_acquire()`, copy each shared input codeword into VTCM, then
  decode from VTCM. This passed correctness but was slower:
  `52.684 us/decode` vs `37.644 us/decode` for direct shared-buffer decode on a
  `1000 x 16` batch.
- Inter-stage workspace: put the small `rs_words` buffer between Reed-Muller
  and Reed-Solomon in VTCM, avoiding input-codeword staging. This also passed
  correctness but did not improve throughput on any parameter set:

| HQC | Direct us/decode | VTCM workspace us/decode | Delta |
| --- | ---: | ---: | ---: |
| HQC-128 | 37.742 | 37.902 | +0.42% |
| HQC-192 | 52.675 | 52.939 | +0.50% |
| HQC-256 | 80.007 | 80.303 | +0.37% |

Interpretation:

- Explicit per-codeword copy into a local aligned DSP buffer is slightly slower
  in this full decode benchmark, adding about `1.68%-2.42%`.
- `Q6_l2fetch_AR` on the next codeword is essentially neutral here
  (`-0.60%` to `+0.25%`). Any benefit is below run-to-run noise at this
  workload size.
- Real VTCM allocation works, but neither tested placement is a valid
  optimization for the current decoder. Codeword staging adds too much copy
  cost, while the available inter-stage workspace is too small to benefit even
  at HQC-192 and HQC-256.
- `malloc`, `rpcmem-cached`, and `rpcmem-uncached` are close once the data is
  inside a batched FastRPC call. This suggests the current decode path is
  compute dominated, not dominated by input codeword movement from the shared
  host buffer.
- The report can now state that memory-transfer/cache management was tested
  with shared-buffer direct read, local staging, L2 prefetch, and rejected VTCM
  placements across HQC-128/192/256. VTCM is intentionally not retained in the
  active benchmark path.
